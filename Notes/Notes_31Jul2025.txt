 First Normal Form (1NF) – Explained Simply
📘 Definition:
A table is in First Normal Form (1NF) if:

All columns contain only atomic (indivisible) values, and

Each column contains values of a single type, and

Each row is uniquely identifiable (i.e., has a primary key).



===============================
      FIRST NORMAL FORM (1NF)
===============================

Definition:
-----------
A table is in First Normal Form (1NF) if:
1. All attributes (columns) contain only atomic (indivisible) values.
2. Each column contains values of the same type.
3. Each row is unique (usually identified by a primary key).

Key Points:
-----------
- No repeating groups or arrays.
- No multiple values in a single cell.
- Each record should be unique.

Example of NOT in 1NF:
----------------------
Table: Students

+-----------+--------+---------------------+
| StudentID | Name   | Subjects            |
+-----------+--------+---------------------+
| 101       | Arjun  | Math, Science       |
| 102       | Priya  | English, History    |

Violation:
- 'Subjects' column has multiple values (not atomic).

Conversion to 1NF:
------------------
Table: StudentSubjects

+-----------+--------+-----------+
| StudentID | Name   | Subject   |
+-----------+--------+-----------+
| 101
--------------------------------------------------------------

2nd normal form
--------------------
The table must be already in 1NF, and each attribute (column) must be functionally dependent on the primary key




Here’s a **Notepad-friendly explanation** of **Second Normal Form (2NF)** — easy to use in lectures, notes, or handouts.

---

```
===============================
      SECOND NORMAL FORM (2NF)
===============================

Definition:
-----------
A table is in Second Normal Form (2NF) **if**:
1. It is already in First Normal Form (1NF), AND
2. All non-key attributes are fully functionally dependent on the **entire primary key**.

Key Concepts:
-------------
- 1NF + No Partial Dependency.
- Partial Dependency occurs when a non-key column depends on only a part of a composite primary key.

Reminder:
---------
- Composite Primary Key: A primary key made of more than one column.

Example of NOT in 2NF:
----------------------
Table: StudentCourses

+----------+----------+------------+--------------+
| StudentID| CourseID | StudentName| CourseName   |
+----------+----------+------------+--------------+
| 1        | 101      | Ravi       | Java         |
| 1        | 102      | Ravi       | Python       |
| 2        | 101      | Kavya      | Java         |

Primary Key: (StudentID, CourseID)

Violations:
- StudentName depends only on StudentID
- CourseName depends only on CourseID
=> Partial dependencies exist => Not in 2NF

Conversion to 2NF:
------------------
Break the table into 3 tables:

1. Students Table:
+-----------+-------------+
| StudentID | StudentName |
+-----------+-------------+
| 1         | Ravi        |
| 2         | Kavya       |

2. Courses Table:
+----------+------------+
| CourseID | CourseName |
+----------+------------+
| 101      | Java       |
| 102      | Python     |

3. Enrollments Table:
+-----------+----------+
| StudentID | CourseID |
+-----------+----------+
| 1         | 101      |
| 1         | 102      |
| 2         | 101      |

Now:
- No partial dependency.
- Each non-key attribute depends on the whole primary key.

End of 2NF Notes.
```

```
=================================
     ORACLE SQL DATA TYPES
=================================

1. CHARACTER DATA TYPES
------------------------
- CHAR(n)
  Fixed-length character string.
  Max: 2000 bytes.

  Example:
    CHAR(10) → Always 10 characters, space-padded if shorter.

- VARCHAR2(n)
  Variable-length string.
  Max: 4000 bytes (can extend with extended mode).

  Example:
    VARCHAR2(20) → Stores up to 20 characters.

- CLOB
  Character Large Object (up to 4 GB of text).

---------------------------------------------------

2. NUMERIC DATA TYPES
-----------------------
- NUMBER(p, s)
  General-purpose number.
  p = precision (total digits)
  s = scale (digits after decimal)

  Example:
    NUMBER(5,2) → Up to 999.99

- INTEGER / INT
  Same as NUMBER(38)

- FLOAT(n)
  Approximate number with n binary digits precision

---------------------------------------------------

3. DATE AND TIME DATA TYPES
-----------------------------
- DATE
  Stores date + time (up to seconds).
  Format: DD-MON-YY or DD-MON-YYYY

  Example: 31-JUL-2025

- TIMESTAMP
  Stores date + fractional seconds.
  More precise than DATE.

- TIMESTAMP WITH TIME ZONE
  Includes time zone offset.

- TIMESTAMP WITH LOCAL TIME ZONE
  Normalized to DB server’s time zone.

---------------------------------------------------

4. BINARY DATA TYPES
---------------------
- RAW(n)
  Stores binary data (up to 2000 bytes).

- LONG RAW
  Stores binary data (up to 2 GB). Deprecated.

- BLOB
  Binary Large Object (up to 4 GB)

---------------------------------------------------

5. LOB DATA TYPES
-------------------
- BLOB  → Binary Large Object (e.g., images, videos)
- CLOB  → Character Large Object
- NCLOB → National Character LOB
- BFILE → External binary files (read-only)

---------------------------------------------------

6. ROWID AND UROWID
---------------------
- ROWID
  Physical address of a row in DB.

- UROWID
  Universal ROWID, supports both physical and logical addresses (used in Index-Organized Tables).

---------------------------------------------------

7. BOOLEAN (PL/SQL only)
--------------------------
- BOOLEAN
  TRUE / FALSE / NULL (only in PL/SQL, not in SQL queries)

---------------------------------------------------
```

```
======================================
      DATA INTEGRITY IN ORACLE SQL
======================================

Definition:
-----------
Data Integrity ensures **accuracy, consistency, and reliability**
of data in a database throughout its lifecycle.

Oracle provides **built-in constraints** to enforce integrity rules
automatically at the database level.

======================================
TYPES OF DATA INTEGRITY & EXAMPLES
======================================

1. DOMAIN INTEGRITY
--------------------
Ensures values in a column fall within a specific range, format, or type.

Enforced using:
  - CHECK constraints
  - NOT NULL constraints
  - Data types

Example:
---------
CREATE TABLE employees (
  emp_id     NUMBER PRIMARY KEY,
  name       VARCHAR2(50) NOT NULL,
  age        NUMBER CHECK (age >= 18 AND age <= 60)
);

- Name cannot be null.
- Age must be between 18 and 60.

--------------------------------------

2. ENTITY INTEGRITY
--------------------
Ensures each row in a table is uniquely identifiable.

Enforced using:
  - PRIMARY KEY constraint

Example:
---------
CREATE TABLE students (
  student_id NUMBER PRIMARY KEY,
  name       VARCHAR2(100)
);

- student_id must be unique and not null.

--------------------------------------

3. REFERENTIAL INTEGRITY
-------------------------
Ensures relationships between tables are valid.
Child table values must match values in the parent table.

Enforced using:
  - FOREIGN KEY constraint

Example:
---------
CREATE TABLE departments (
  dept_id   NUMBER PRIMARY KEY,
  dept_name VARCHAR2(100)
);

CREATE TABLE employees (
  emp_id   NUMBER PRIMARY KEY,
  emp_name VARCHAR2(100),
  dept_id  NUMBER,
  CONSTRAINT fk_dept FOREIGN KEY (dept_id)
    REFERENCES departments(dept_id)
);

- You cannot assign a non-existent dept_id to an employee.

--------------------------------------

4. USER-DEFINED INTEGRITY
--------------------------
Custom business rules enforced using:
  - Triggers
  - Application logic
  - Procedures

Example:
---------
A rule that salary cannot increase by more than 50% in one update.

CREATE OR REPLACE TRIGGER salary_check
BEFORE UPDATE ON employees
FOR EACH ROW
WHEN (NEW.salary > OLD.salary * 1.5)
BEGIN
  RAISE_APPLICATION_ERROR(-20001, 'Salary hike too high!');
END;

--------------------------------------

SUMMARY TABLE:
--------------
| Integrity Type      | Enforced By         | Purpose                        |
|---------------------|---------------------|--------------------------------|
| Domain Integrity     | NOT NULL, CHECK     | Valid column values            |
| Entity Integrity     | PRIMARY KEY         | Unique identification          |
| Referential Integrity| FOREIGN KEY         | Valid table relationships      |
| User-Defined         | Triggers, Logic     | Custom business rules          |

========================================
HANDS-ON TASK IDEAS (for participants)
========================================

2. Apply CHECK and NOT NULL constraints.
3. Try inserting:
   - A null into a NOT NULL column → Should fail
   - A wrong FK value → Should fail
4. Add a trigger to enforce a user-defined integrity rule.

End of Data Integrity Notes.
```

You're welcome! Let's dive into what **is** and **is not** allowed with `CHECK` constraints in Oracle.

---

## ✅ What is **Possible** in `CHECK` Constraints

### 1. **Column-level conditions**

You can enforce rules on the values of one or more columns:

```sql
CHECK (salary >= 20000)
CHECK (salary BETWEEN 20000 AND 200000)
```

---

### 2. **Multiple columns in the same condition**

```sql
CHECK (start_date < end_date)
```

---

### 3. **Logical operators**

You can use `AND`, `OR`, and `NOT`:

```sql
CHECK (age >= 18 AND age <= 60)
CHECK (department = 'HR' OR department = 'IT')
CHECK (NOT (status = 'inactive' AND balance > 0))
```

---

### 4. **IN, LIKE, IS NULL**

```sql
CHECK (gender IN ('M', 'F', 'O'))
CHECK (email LIKE '%.com')
CHECK (middle_name IS NULL OR LENGTH(middle_name) > 1)
```

---

### 5. **Simple expressions**

```sql
CHECK (quantity * price <= 10000)
```

---

### 6. **CHECK on nullable columns**

If the column is `NULL`, the constraint is not violated:

```sql
CHECK (score >= 0 AND score <= 100) -- NULL values pass this check
```

---

## ❌ What is **Not Possible** in `CHECK` Constraints

### 🚫 1. **Subqueries**

You cannot use SELECT inside a CHECK:

```sql
-- ❌ Invalid
CHECK (salary > (SELECT AVG(salary) FROM employees))
```

---

### 🚫 2. **Functions that access database state**

No user-defined functions, and most Oracle built-ins like `SYSDATE`, `CURRENT_DATE`, etc.:

```sql
-- ❌ Invalid
CHECK (hire_date <= SYSDATE)
```

Only deterministic functions like `LENGTH`, `UPPER`, `ROUND` are sometimes allowed.

---

### 🚫 3. **Referencing other tables**

You cannot enforce foreign key-like logic using `CHECK`:

```sql
-- ❌ Invalid
CHECK (dept_id IN (SELECT dept_id FROM departments))
```

Use `FOREIGN KEY` constraints for this.

---

### 🚫 4. **PL/SQL logic**

No IF-ELSE, CASE statements, or procedure/function calls.

---

### 🚫 5. **Cross-row validation**

You can't check if a value already exists in another row or compare between rows.

```sql
-- ❌ Invalid
CHECK (salary < ALL (SELECT salary FROM employees WHERE department_id = 10))
```

Use **triggers** or application logic for this kind of validation.

---

## ✅ ORACLE SQL — INSERT Statement Variants

---

### 🔹 Syntax #1: Insert using all columns (in order)

```sql
INSERT INTO PRODUCT VALUES (1, 'PEN', 10, 'STATIONERY');
```

> ⚠️ Not recommended if columns are added/removed later — column order may break!

---

### 🔹 Syntax #2: Insert using specific columns (safe)

```sql
INSERT INTO PRODUCT (ID, NAME, PRICE) VALUES (2, 'SHARPNER', 10);
```

> ✅ Recommended: safe against future column changes. Default values will apply if not specified.

---

### 🔹 Syntax #3: Insert using `DEFAULT` keyword

```sql
INSERT INTO PRODUCT (ID, NAME, PRICE, CATEGORY)
VALUES (3, 'LG 55 inch TV', 50000, DEFAULT);
```

> ✅ Use `DEFAULT` explicitly when you want Oracle to apply the column's default value.

---

### 🔹 Syntax #4: Insert multiple rows using `INSERT ALL`

```sql
INSERT ALL
  INTO PRODUCT (ID, NAME, PRICE, CATEGORY) VALUES (4, 'Toothpaste', 45.50, 'PERSONAL CARE')
  INTO PRODUCT (ID, NAME, PRICE) VALUES (5, 'Pen', 15.00) -- default CATEGORY
SELECT * FROM dual;
```

> ✅ Inserts multiple rows efficiently with one statement.

---

### 🔹 Syntax #5: Insert using `SELECT` from another table

```sql
INSERT INTO PRODUCT (ID, NAME, PRICE, CATEGORY)
SELECT ID, NAME, PRICE, CATEGORY FROM TEMP_PRODUCTS;
```

> 📥 Used for **copying/migrating** data between tables.

---

### 🔹 Syntax #6: Conditional Insert using `INSERT ALL ... WHEN`

```sql
INSERT ALL
  WHEN CATEGORY = 'GADGET' THEN
    INTO ELECTRONICS (ID, NAME, PRICE) VALUES (ID, NAME, PRICE)
  WHEN CATEGORY = 'STATIONERY' THEN
    INTO STATIONERY (ID, NAME, PRICE) VALUES (ID, NAME, PRICE)
SELECT ID, NAME, PRICE, CATEGORY FROM PRODUCT;
```

> 🔁 Used to **split and insert into multiple tables** based on a condition.

---

### 🔹 Syntax #7: Insert using `RETURNING INTO`

```sql
DECLARE
  new_id NUMBER;
BEGIN
  INSERT INTO PRODUCT (ID, NAME, PRICE, CATEGORY)
  VALUES (1001, 'Charger', 999, 'GADGET')
  RETURNING ID INTO new_id;

  DBMS_OUTPUT.PUT_LINE('Inserted ID: ' || new_id);
END;
```

> 🎯 Captures generated values like `ID`, useful in PL/SQL blocks.

---

## ℹ️ Notes:

* Oracle **does not support** `INSERT INTO ... VALUES (), (), ()` syntax (like MySQL).
* Use **`INSERT ALL`** for multiple rows.
* Use **column list** always for better maintainability.

Here’s a **complete, notepad-friendly explanation** of **Oracle Transactions**, including `COMMIT`, `SAVEPOINT`, `ROLLBACK`, **ACID properties**, **concurrency issues**, and **isolation levels** — with examples.

---

## ✅ 1. What is a Transaction?

A **transaction** is a logical unit of work made up of one or more SQL statements that are executed together.

It begins with the first **DML** (INSERT, UPDATE, DELETE) and ends with a:

* `COMMIT` — to make the changes permanent
* or `ROLLBACK` — to undo the changes

---

## ✅ 2. COMMIT

* **Makes all changes permanent**
* Releases all locks

```sql
UPDATE EMPLOYEES SET SALARY = SALARY + 1000 WHERE DEPT_ID = 10;
COMMIT;
```

---

## ✅ 3. ROLLBACK

* **Undo** all changes since the last `COMMIT`
* Releases all locks

```sql
DELETE FROM EMPLOYEES WHERE EMP_ID = 101;
ROLLBACK;  -- Undo the DELETE
```

---

## ✅ 4. SAVEPOINT

* Creates a **named checkpoint** in a transaction.
* You can **ROLLBACK to that point** instead of undoing the whole transaction.

```sql
SAVEPOINT sp1;

UPDATE EMPLOYEES SET SALARY = 5000 WHERE EMP_ID = 101;

SAVEPOINT sp2;

DELETE FROM EMPLOYEES WHERE DEPT_ID = 20;

ROLLBACK TO sp2; -- Undo DELETE only

COMMIT; -- Commit remaining changes
```

---

## ✅ 5. ACID Properties

A reliable transaction must follow **ACID** properties:

| Property            | Description                                                     |
| ------------------- | --------------------------------------------------------------- |
| **A - Atomicity**   | All steps in the transaction complete or none do.               |
| **C - Consistency** | Ensures database moves from one valid state to another.         |
| **I - Isolation**   | Transactions do not interfere with each other.                  |
| **D - Durability**  | Once committed, changes persist even after crash/power failure. |

---

## ✅ 6. Concurrency Issues

When multiple transactions run at the same time, **concurrency control** is critical. Common issues include:

| Issue                   | Description                                                                            |
| ----------------------- | -------------------------------------------------------------------------------------- |
| **Dirty Read**          | T2 reads uncommitted data from T1                                                      |
| **Non-repeatable Read** | T1 reads a row; T2 updates it; T1 reads again and sees different data                  |
| **Phantom Read**        | T1 queries a condition; T2 inserts matching rows; T1 queries again and gets extra rows |

---

## ✅ 7. Isolation Levels (Oracle)

Controls how/if one transaction can see another transaction’s uncommitted data.

| Isolation Level              | Description                                                 |
| ---------------------------- | ----------------------------------------------------------- |
| **READ COMMITTED** (Default) | Only sees committed changes. Prevents **dirty reads**.      |
| **SERIALIZABLE**             | Full isolation. Prevents all concurrency issues but slower. |
| **READ ONLY**                | No DML allowed. Like SERIALIZABLE but for queries only.     |

Set using:

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

---

## ✅ Example: Concurrency with Isolation

### Transaction 1 (T1):

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT * FROM PRODUCT WHERE CATEGORY = 'STATIONERY';
```

### Transaction 2 (T2) in parallel:

```sql
INSERT INTO PRODUCT VALUES (999, 'Sketch Pen', 45, 'STATIONERY');
COMMIT; -- Blocked if T1 is SERIALIZABLE
```
